# نقشهٔ معماری — فرمان، تراکنش، و رویداد

> **وضعیت: پیشنهاد.** هیچ کدی بر اساسِ این سند نوشته نشده. پیاده‌سازی
> فقط بعد از تأییدِ شما شروع می‌شود، مرحله‌به‌مرحله.

## ۰. حکمِ کوتاه

| الگو | حکم |
|---|---|
| **Command** (فرمان) | **بله** — هستهٔ کار |
| **Unit of Work** (تراکنشِ اتمی) | **بله** — بدونِ آن بقیه بی‌معناست |
| **Transactional Outbox** (رویدادِ ماندگار) | **بله** — این همان چیزی است که ارزشِ ده‌ساله دارد |
| **Event Bus درون‌حافظه‌ای** | **نه** — و دلیلش را در بخشِ ۱ می‌گویم |
| **Event Sourcing** | **نه** |
| **CQRSِ کامل** | **نه** — نیمهٔ خواندنش از قبل هست |

پیشنهادِ شما در جوهرِ خودش درست است. تنها جایی که تغییرش می‌دهم
**شکلِ رویداد** است: به‌جای گذرگاهِ درون‌حافظه‌ای، یک **جدولِ رویداد که
داخلِ همان تراکنش نوشته می‌شود**.

---

## ۱. چرا گذرگاهِ درون‌حافظه‌ای برای *این* پروژه اشتباه است

دو دلیلِ فنی، هر دو سنجیده‌شده در همین کد.

### الف. گذرگاه از قبل وجود دارد و اسمش Room است

    ۵۸ جریانِ Flow<List<…>> در DAOها

هر صفحه با `Flow` به دیتابیس وصل است. وقتی چیزی نوشته می‌شود،
`InvalidationTracker` خودِ Room همهٔ ناظرانِ آن جدول را بیدار می‌کند و
داشبورد، انبار و دفتر **خودشان** تازه می‌شوند.

یعنی «`InventoryChanged` منتشر شود تا داشبورد به‌روز شود» کاری است که
**همین الان انجام می‌شود**. افزودنِ گذرگاه برای این کار، مسیرِ دومی
می‌سازد که همان کار را ضعیف‌تر انجام می‌دهد — و دو مسیر یعنی روزی
از هم می‌افتند.

### ب. گذرگاهِ درون‌حافظه‌ای **همان اشکالی را برمی‌گرداند که داریم رفعش می‌کنیم**

مشکلِ امروز *dual write* است: انبار نوشته می‌شود، پول جدا نوشته
می‌شود، و اگر وسطش بمیریم دفتر نیمه‌کاره می‌ماند.

یک گذرگاهِ درون‌حافظه‌ای دقیقاً همین را در جای تازه‌ای می‌سازد:

| اتفاق | نتیجه |
|---|---|
| رویداد شلیک شود، بعد تراکنش برگردد (rollback) | اثرِ جانبیِ **خیالی** — اعلانِ فروشی که هرگز ثبت نشد |
| تراکنش commit شود، بعد پروسه بمیرد | اثرِ جانبیِ **گم‌شده** — فروش هست، لاگِ حسابرسی نیست |

روی اندروید حالتِ دوم فرضی نیست: سیستم هر لحظه می‌تواند پروسه را بکشد.

**راهِ درست:** رویداد یک **ردیفِ دیتابیس** است که در همان تراکنشِ
تغییرِ وضعیت نوشته می‌شود. یا هر دو هستند یا هیچ‌کدام. بعد از commit،
یک توزیع‌کننده آن‌ها را می‌خواند و به مصرف‌کننده‌ها می‌دهد؛ اگر پروسه
بمیرد، دفعهٔ بعد از همان‌جا ادامه می‌دهد.

## ۲. معماریِ پیشنهادی

```
        صفحه / ViewModel
               │  فرمان (دادهٔ خالص)
               ▼
        ┌──────────────┐
        │ CommandBus   │  یک نقطهٔ ورود برای هر تغییرِ وضعیت
        └──────┬───────┘
               │
               ▼
        ┌──────────────────────────────────────┐
        │  Tx.atomic {                         │   ← مرزِ هشتم
        │     handler(cmd, ctx)                │
        │       ├── نوشتنِ وضعیت (DAOها)        │
        │       └── ctx.emit(Event…)  ──┐      │
        │  }                            │      │
        └───────────────────────────────┼──────┘
                                        ▼
                              جدولِ `domain_events`
                          (داخلِ همان تراکنش، پس اتمی)
                                        │
                    ── commit شد ──────►│
                                        ▼
                              ┌──────────────────┐
                              │ EventDispatcher  │  at-least-once
                              └────────┬─────────┘
                    ┌──────────────────┼──────────────────┐
                    ▼                  ▼                  ▼
              AuditProjector     Notifications        SyncOutbox
              (لاگِ حسابرسی)      (کمبود، حقوق)      (چنددستگاهی، آینده)
```

### قطعه‌ها

**`Command`** — دادهٔ خالص، بی رفتار. مثال:

```kotlin
data class RecordSaleReturn(
    val saleId: UUID,
    val qty: Int,
    val refundCash: Boolean,
    val cashBox: String = "WALLET"
) : Command<Unit>
```

**`CommandHandler`** — تنها جایی که آن تغییر انجام می‌شود:

```kotlin
interface CommandHandler<C : Command<R>, R> {
    suspend fun handle(cmd: C, ctx: CommandContext): R
}
```

**`CommandContext`** — دسترسیِ DAOها + `emit`. مصرف‌کننده‌ها را
نمی‌شناسد.

**`Tx`** — مرزِ هشتم، دقیقاً به سبکِ هفت مرزِ موجود:

```kotlin
// :core
interface Tx { suspend fun <T> atomic(block: suspend () -> T): T }
// :app     → db.withTransaction { … }
// :desktop → معادلش
```

**`DomainEvent`** — رویدادِ ماندگار با شناسه، نوع، نسخه، بارِ JSON،
زمان، و کاربر.

## ۳. چگونه با تراکنشِ اتمی هماهنگ می‌شود

این نقطهٔ اصلیِ طراحی است:

1. `CommandBus` فرمان را می‌گیرد و `Tx.atomic { … }` باز می‌کند.
2. Handler وضعیت را می‌نویسد و `ctx.emit(...)` می‌زند. `emit` **هیچ
   چیزی را شلیک نمی‌کند** — فقط یک ردیف در `domain_events` می‌نویسد،
   داخلِ همان تراکنش.
3. تراکنش commit می‌شود → وضعیت و رویداد **با هم** ماندگار شدند.
4. `EventDispatcher` (خارج از تراکنش) رویدادهای پردازش‌نشده را به
   ترتیبِ `seq` می‌خواند و به مصرف‌کننده‌ها می‌دهد، بعد علامتِ
   «پردازش شد» می‌زند.

**تحویل at-least-once است، نه exactly-once.** پس هر مصرف‌کننده باید
idempotent باشد — یعنی پردازشِ دوبارهٔ یک رویداد اثرِ تازه‌ای نداشته
باشد. این یک قاعدهٔ صریح است، نه جزئیات: با `eventId` یکتا و
`INSERT OR IGNORE` ساده به‌دست می‌آید.

**نکتهٔ حیاتی:** هیچ مصرف‌کننده‌ای اجازه ندارد وضعیتِ مالی را عوض کند.
مصرف‌کننده‌ها فقط **بازتاب** می‌سازند (لاگ، اعلان، صفِ همگام‌سازی).
اگر اثری بخشی از درستیِ حساب است، باید **داخلِ همان فرمان** باشد نه در
یک handler — وگرنه دوباره به همان نیمه‌کارگی رسیده‌ایم.

## ۴. رویدادها

### چالشی روی فهرستِ پیشنهادیِ شما

`InventoryChanged` و `CustomerBalanceChanged` را **حذف می‌کنم** و
دلیلش مهم است: اینها **نتیجه**‌اند، نه **واقعه**. موجودی به این دلیل
عوض شد که فروشی رخ داد یا خریدی یا شمارشی. اگر هم علت و هم نتیجه را
منتشر کنیم، دو روایت از یک اتفاق داریم و روزی از هم می‌افتند — و
مصرف‌کننده نمی‌داند کدام را باور کند.

رویداد باید **چیزی باشد که در دنیای واقعی افتاد**، با نامِ گذشته.

### فهرستِ پیشنهادی

| رویداد | از کدام فرمان | بارِ داده |
|---|---|---|
| `SaleRecorded` | `SellInvoice` | کد، مشتری، ردیف‌ها، جمع، بها، نقدِ دریافتی |
| `SaleReturned` | `RecordSaleReturn` | شناسهٔ فروش، تعداد، مبلغ، نقدی یا اعتباری |
| `PaymentReceived` | `AddCustomerPayment` | مشتری، مبلغ، صندوق |
| `PaymentMade` | `PaySupplier` / `PayWage` | طرف، مبلغ، صندوق، بابت |
| `MaterialPurchased` | `RecordPurchase` | تأمین‌کننده، اقلام، مبلغ، نقد/نسیه |
| `PurchaseReturned` | `RecordPurchaseReturn` | همان، وارونه |
| `StockRecounted` | `RecountStock` | قلم، شمارشِ قبلی و جدید، تفاوتِ ارزش |
| `OrderCreated` | `CreateOrder` | کد، طرح، تعداد، مشتری |
| `OrderStageChanged` | `ChangeOrderStage` | کد، از، به |
| `PartialDelivered` | `DeliverPartial` | کد، تعداد، مرحله |
| `WageAccrued` | `AssignSewing` / `CompleteAssignment` | خیاط، سفارش، مبلغ |
| `AttendanceRecorded` | `RecordAttendance` | کارمند، ورود/خروج |
| `DataReset` | `ResetData` | دامنه‌های پاک‌شده |

سیزده رویداد. عمداً کم — هر رویداد یک قرارداد است و قرارداد را نمی‌شود
راحت پس گرفت.

## ۵. مصرف‌کننده‌ها

| مصرف‌کننده | چه رویدادهایی | چه می‌کند |
|---|---|---|
| **AuditProjector** | همه | لاگِ حسابرسی می‌سازد |
| **NotificationHandler** | `MaterialPurchased`, `SaleRecorded`, `StockRecounted` | کمبودِ موجودی، یادآوری |
| **WageReminder** | `WageAccrued` | تسویهٔ کارمزد |
| **SyncOutbox** *(آینده)* | همه | صفِ تغییر برای دستگاه‌های دیگر |
| **StatsProjector** *(اختیاری)* | همه‌ی مالی | تجمیعِ ازپیش‌محاسبه‌شدهٔ داشبورد |
| **PluginHost** *(آینده)* | اشتراکی | افزونه‌ها |

### چرا `AuditProjector` تنهایی ارزشِ کار را می‌دهد

    ۲۵ تابعِ نویسنده در Repo، ۱۱ تای‌شان **بدونِ** فراخوانیِ audit

از جمله `addCustomerPayment` و `recordSupplierCredit` — یعنی **دو
عملیاتِ پولی که هیچ ردی در حسابرسی نمی‌گذارند**. علتش ساده است: `audit`
دستی صدا زده می‌شود و آدم فراموش می‌کند.

با مشتق شدنِ حسابرسی از رویداد، فراموش کردن **ناممکن** می‌شود: هر
فرمانی که رویداد بدهد، خودبه‌خود حسابرسی دارد. و یک بررسیِ تازه می‌تواند
نگه دارد که هر فرمان دستِ‌کم یک رویداد بدهد.

## ۶. حذفِ وابستگیِ مستقیم بینِ ماژول‌ها

امروز `Repo` همه‌چیز را می‌شناسد: فروش، انبار، حقوق، اعلان، شبکه.

بعد:

- `SalesService` فقط `SaleRecorded` می‌دهد. **نمی‌داند** کسی اعلان
  می‌فرستد یا همگام‌سازی می‌کند.
- `NotificationHandler` فقط رویداد را می‌شناسد، نه `SalesService` را.
- افزودنِ مصرف‌کنندهٔ تازه **هیچ فایلِ موجودی را عوض نمی‌کند**.

جهتِ وابستگی یک‌طرفه می‌شود: `فرمان → رویداد → مصرف‌کننده`. هیچ حلقه‌ای.

## ۷. اثر روی چهار محور

**تست‌پذیری — بزرگ‌ترین سود.**
امروز ۷ شبیه‌سازِ قاعده، قاعده را **بیرونِ** کد در پایتون پیاده می‌کنند
و بعد می‌سنجند که متنِ کاتلین همان را بگوید. این بهترین کاری بود که
بدونِ تست‌پذیری می‌شد کرد، ولی همچنان *متن* را می‌سنجد.

با فرمان، هر قاعده با دادهٔ خالص آزموده می‌شود:

```kotlin
val events = handler.handle(RecordSaleReturn(id, 2, refundCash = true), ctx)
assertEquals(18_000, ctx.stateOf(sale).netTotal)
```

یعنی از **«کد این را می‌گوید»** به **«کد این کار را می‌کند»**.

**نگهداری.** غولِ ۲٬۹۹۴ خطی به ۱۳ فرمان می‌شکند که هرکدام یک مسئولیت
دارند. دو نفر می‌توانند هم‌زمان کار کنند.

**مقیاس‌پذیری.** جدولِ رویداد ترتیبِ سراسری می‌دهد؛ `StatsProjector`
می‌تواند تجمیعِ داشبورد را ازپیش حساب کند و آن ۹ ViewModelی که کلِ
جدولِ سفارش را می‌خوانند حذف شوند.

**نسخه‌های آینده.**
- *Sync / چنددستگاهی*: جدولِ رویداد **همان لاگِ همگام‌سازی است**. بدونِ
  آن، همگام‌سازی یعنی مقایسهٔ کلِ جدول‌ها.
- *Cloud*: همان outbox بالا فرستاده می‌شود.
- *Plugin*: افزونه رویداد مصرف می‌کند، نه کدِ داخلی.

## ۸. مقایسهٔ الگوها

| الگو | برای این پروژه | چرا |
|---|---|---|
| **Unit of Work** | ✅ ضروری | همان تراکنشِ اتمی. بدونِ آن هیچ‌کدام از بقیه معنا ندارد. |
| **Command** | ✅ | یک نقطهٔ ورود برای هر تغییر؛ تست‌پذیری و شکستنِ غول. |
| **Transactional Outbox** | ✅ | تنها راهِ رویدادِ بی‌گم‌شدن روی اندروید. و لاگِ همگام‌سازیِ آینده. |
| **Event Bus درون‌حافظه‌ای** | ❌ | Room از قبل این کار را می‌کند؛ و dual-write را برمی‌گرداند. |
| **CQRS** | ➖ نیمه | نیمهٔ خواندن از قبل هست (Room Flow). نیمهٔ نوشتن همان Command است. پایگاهِ خواندنِ جدا لازم نیست. |
| **Event Sourcing** | ❌ | رویداد به‌عنوانِ منبعِ حقیقت یعنی بازنویسیِ ۴۳ موجودیت و ۴۲ مهاجرت، و بازسازیِ وضعیت روی گوشیِ ارزان. **ژورنالِ دوطرفه از قبل ردیابی‌پذیری را می‌دهد** — سودِ اصلیِ ES را بی هزینه‌اش داریم. |

## ۹. آیا راهِ بهتری هست؟

بله، و همین است — با یک تفاوتِ ترتیب که مهم است:

**ارزشِ ده‌ساله در «فرمان + تراکنش + لاگِ ماندگار» است، نه در
«گذرگاه».** گذرگاه کم‌ارزش‌ترین قطعهٔ این طرح است و حذفش هیچ چیزی کم
نمی‌کند.

اگر فردا کار متوقف شود، ترتیبِ ارزش این است:

1. `Tx.atomic` — درستیِ دفتر
2. `Command` — تست‌پذیری و شکستنِ غول
3. `domain_events` — حسابرسیِ خودکار، و لاگِ همگام‌سازی
4. `Dispatcher` + مصرف‌کننده‌ها — راحتی

هر مرحله به‌تنهایی ارزش دارد و بدونِ مرحلهٔ بعدی هم مفید است.

## ۱۰. نقشهٔ مهاجرت

هیچ مرحله‌ای صفحه‌ای را عوض نمی‌کند. `Repo` به‌عنوانِ نما (facade)
می‌ماند و به فرمان‌ها واگذار می‌کند، پس ۳۹ صفحه دست‌نخورده‌اند.

| گام | کار | ریسک | برگشت‌پذیری |
|---|---|---|---|
| **۰** | مرزِ `Tx` (هشتمین مرز) + بررسیِ نگهبان | کم | کامل |
| **۱** | پیچیدنِ هر تابعِ پولیِ موجود در `tx.atomic` — **بدونِ** بازآرایی | کم | کامل |
| **۲** | فرمانِ آزمایشی: `RecordSaleReturn` (کوچک، تازه لمس‌شده، ۸ تست دارد) | کم | کامل |
| **۳** | جدولِ `domain_events` + `emit` — نوشته می‌شود، هنوز خوانده نمی‌شود | متوسط (مهاجرت) | افزودنی |
| **۴** | `Dispatcher` + `AuditProjector`؛ `audit()`های دستی دامنه‌به‌دامنه برداشته شوند | متوسط | مرحله‌ای |
| **۵** | بقیهٔ فرمان‌ها، یک دامنه در هر کامیت | کم | مرحله‌ای |
| **۶** | مصرف‌کنندهٔ همگام‌سازی روی همان outbox | — | آینده |

**گام ۱ به‌تنهایی مهم‌ترین بخشِ کلِ این سند است.** بحرانی‌ترین اشکال را
می‌بندد و هیچ معماریِ تازه‌ای نمی‌خواهد.

### سازگاری

- `Repo` API عمومی‌اش را نگه می‌دارد → صفحه‌ها عوض نمی‌شوند.
- `domain_events` جدولِ **تازه** است → فقط `CREATE TABLE`، بدونِ دست
  زدن به دادهٔ موجود.
- حسابرسیِ قدیمی حذف نمی‌شود؛ تا وقتی که بازتابِ تازه هم‌ارز بودنش
  ثابت شود، هر دو کنارِ هم می‌مانند.

### دو تصمیم که تأییدِ شما را می‌خواهد

**۱. `DB_VERSION` از ۶۱ به ۶۲.**
قاعدهٔ نوشته‌شده در `docs/WINDOWS.md` می‌گوید «هیچ فازی نباید
`DB_VERSION` را دست بزند». آن قاعده برای فازهای ویندوز بود تا طرحِ
دیتابیس وسطِ کار تکان نخورد. جدولِ رویداد یک مهاجرتِ تازه لازم دارد و
عمداً این را **نمی‌کنم مگر شما بگویید**. بدونِ آن، گام‌های ۰ تا ۲
همچنان کاملاً ممکن‌اند.

مهاجرت افزودنی و بی‌خطر است (`CREATE TABLE` + ایندکس)، ولی باید در
`AppDatabase` و `DesktopDatabase` **هر دو** بیاید — بررسیِ `dbtwin`
اگر یکی جا بماند قرمز می‌شود — و در `ResetPlan` دسته‌بندی شود، وگرنه
`resetcheck` قرمز می‌شود. یعنی نگهبان‌های موجود این کار را پوشش
می‌دهند.
